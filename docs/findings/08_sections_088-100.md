## 89. Correction to section 87's investigation, and a regression guard -- design registered before implementing

**Correction.** Section 87's investigation said that training starts at
n = 2. That is wrong: the search starts at level 1 (`--start-level 1`).
The real gap:
- A champion is checked only *forward*. The invariance lookahead runs
  the unmutated program on the following levels.
- It is never re-checked on the levels *before* the one where it was
  found.
- The rejected min_gap programs were found at N = 3 (80/80), cascaded
  forward to N = 8, and broke at n = 1. By then the search had
  mutated away the accumulator's `= 0` initialization, and no score
  ever covered n = 1 again.

The section 88 decision stands; the cause it cites (n = 1 rejections hit
both arms equally) is unchanged.

**Regression guard, `--regression-guard K`** (opt-in; 0 = off and
byte-identical). From the second level on, each level's scoring set also
contains the first K instances of every earlier level. Those include the
exhaustive tiny arrays, which come first in the array problems'
generators. A program that breaks smaller n then loses score at once and
is outranked, instead of being discovered only by the verifier. **K = 12**,
fixed before running. That costs at most 12 x (levels so far) extra
instances per evaluation.

**A/B.**
- (i) min_gap and max_gap_sorted at 30 matched seeds (40000-40029).
- (ii) Every registered array/scalar problem at 10 seeds (41000-41009),
  base (current default) vs RG (`--regression-guard 12`), per-seed
  `--benchmark`, `--step-limit 20000`.

**Predictions.**
1. In (i), "failed exhaustively at n=1" rejections drop to <= 1 per
   problem under RG (base: about 1/4 to 1/3 of seeds).
2. In (i), min_gap: RG >= base + 4; max_gap_sorted: RG >= base + 2.
3. In (ii), no problem drops by more than 1. Drops of 2 on the four
   sensitive problems are retested at 30 seeds.

**Decision rule, fixed now.** If 1, 2 and 3 hold, `--regression-guard 12`
becomes the default. Time is not a gate, but RG's wall cost will be
reported, per section 88's tracking item.

## 90. Follow-piece extensions: trailing node and loop length -- design registered before implementing

The fourth and last of section 79's gaps. The follow piece (sections
77-79) walks pointers but keeps neither the node before the end
(last_node) nor a second walk around the cycle it reached (cycle_length).

**`--follow-extended`** (opt-in, byte-identical when off) adds two
relations to the follow block's draw, which becomes six-way when the flag
is on:
- **`Trailing`**: acc = the last in-range node visited. Before advancing,
  `acc = p`. If the walk never ended (still in range after the v0 cap),
  acc = nodes (the null value). An empty walk also yields nodes.
- **`LoopLength`**: after the capped walk, if p is still in range (so
  on a cycle), walk once more from p, counting steps until p returns to
  where it started; acc = that count, 0 if the walk ended.

**An honest limit.** These two relations are narrow, and each is close to
one target's algorithm. No post-freeze problem I could write is reachable
by them without being a restatement of a target. This piece therefore
tests reach on the two targets plus two new rulers, *not* generalization.
The cost of six-way dilution falls on cycle, walk_length and
visits_zero, which the gate (section 79) confines to pointer-like
inputs.

**Post-freeze rulers** (written after the freeze, base-checked first):
- `cycle_entry`: the first node of the cycle the walk enters (n if
  none);
- `second_last_node`: the node before the last node (n if none).

**A/B.** The seven pointer-like problems (cycle, walk_length,
visits_zero, cycle_length, last_node, graph_reachability, substring)
plus the two rulers, 30 matched seeds, base vs FX. Non-pointer problems
are byte-identical by section 79's gate. A 3-seed spot check confirms
this, as in section 79.

## 94. `--restart-on-stall K` and `--wall-seconds S` (opt-in) -- implementation

Motivated by section 93 (many short seeds beat one long run on algorithmic
diversity): make the restart happen inside one process, triggered by the
run itself rather than by a fixed per-seed wall slice.

**Mechanism** (`BeamSearch::run`, `SearchConfig::restartOnStall`/`wallSeconds`):
- Stall = the highest level reached in the current run has not risen for
  K consecutive size steps (divergence-window steps count, so K must
  exceed `--post-solve-sizes`).
- On stall: empty beam, fresh `Dedup`, annealing walker and divergence
  window reset, back to `startLevel` at size 1, and a new search seed
  drawn from a master stream seeded by `--seed`. Each record's `seed`
  field is the seed of the run that found it.
- Kept across restarts: the archive (`solutions`, its program@level dedup)
  and cached instance sets. Problem instances stay those of the master seed.
- `--max-program-size` now bounds total size steps across restarts
  (identical to before without restarts); `--wall-seconds` stops cleanly
  at a size-step boundary and saves the archive normally.
- With `--restart-on-stall` and no `--seed`, the master seed is random and
  printed (`[seed] master seed X (random; replay with --seed X)`).

**Checks.**
- `make test` 190/190; 3 new tests
  (`restart_on_stall_restarts_a_stuck_run_and_keeps_the_archive`,
  `restart_on_stall_off_never_restarts`, `wall_seconds_stops_the_run_early`).
- Off by default and byte-identical: sorting, seed 3, max-n 12, beam 200,
  600 candidates, 1 thread -- same log md5 as the previous HEAD build.
- Smoke (`data/restart_smoketest_20261010/`, K=300, 600 s, random seed):
  stops at the wall budget, reaches N=26, no restart yet (still climbing).

**Calibration for the A/B.** In section 92 the run spent 2029 size steps
at N=37 (~8 s each, ~4.5 h); N=1, 2 and 32 took 151 each (one window).
K=300 is therefore ~40 min of no progress at N=37, K=200 ~27 min.
The A/B against section 93 (8 seeds x 20 min, same profile, 2 h 40 compute)
is still to be designed and registered.

2. Only linear/Kadane programs: held.
3. More classes in the restart arm, all linear: held (25 vs 12).

extra classes are Kadane with different junk.

**Reading.** On a problem with several textbook algorithms, the search
finds only the smallest correct one. Kadane is about 45 nodes and is found
at N=2 in a minute; the quadratic and cubic scans are larger and never
win a size-ordered race, and the divergence window only keeps
alternatives that also solve the current N, which Kadane already does.
Diversity here is bounded by the search order (smallest program first),
not by budget or seeds. Finding the slower algorithms would need an
explicit novelty objective (e.g. reward a correct program whose cost
profile differs from every archived one), not more restarts.

## 98. Cost-profile novelty -- design registered before implementing

**Problem** (sections 92-96). More budget, more seeds and restarts only
multiply variants of the algorithms already found. On max_subarray_sum the
smallest correct program (Kadane, ~45 nodes, N=2) wins the size-ordered
race; the divergence window then archives Kadane with different junk,
because it accepts any new program text that solves the current N. Also,
every run since section 92 used `--speed-bonus-weight 0.02`, which rewards
the fastest correct program and so actively pushes away from O(n^2)/O(n^3)
alternatives.

**Profile.** For a candidate that fully solves the current level, run it on
the instances of three probe levels (current N, 2N, 4N, capped at
`--max-n`) and record mean interpreter steps per level. The profile is
`(log steps(N), fitted exponent over the three levels)`. Generic: any
problem with levels, no problem-specific code. Cost: computed only for
full-solve candidates in the top of the scored pool, not for every
candidate.

**Mechanism** (opt-in `--profile-novelty W`):
1. Archive gate: during the divergence window a new champion is archived
   only if its exponent differs from every archived champion's by more than
   0.3, or its log-steps by more than log(1.5). This replaces "new program
   text" and removes junk padding from the archive.
2. Fitness bonus: a full-solve candidate gets `+ W * min(1, d / 0.5)`,
   where d is its exponent distance to the nearest archived champion. It
   is added after the speed bonus, so it can outweigh it.
3. Nothing changes outside the divergence window or before the first full
   solve of a level.

**A/B** (matched seeds 1-8, section 96 control protocol, max-n 64):
- max_subarray_sum: control (current profile) vs `--profile-novelty 0.5`;
  also an arm with `--speed-bonus-weight 0` and no novelty, to separate
  "the speed bonus suppresses slow algorithms" from "novelty finds them".
- sorting (seeds 1-8, 20 min each): control vs `--profile-novelty 0.5`.
- Metric: families by `scripts/triage_sorting.py` (exponent ~1, ~2, ~3,
  n log n), classes, archive size.

**Predictions.**
1. max_subarray_sum with novelty archives at least one quadratic (exponent
   ~2) correct program in at least 4 of 8 seeds; control archives none.
2. The speed-bonus-off arm alone archives no quadratic program: the size
   ordering, not the speed bonus, is the main blocker.
3. Archive sizes drop sharply under the novelty gate (junk variants no
   longer archived), with no loss of families.
4. Sorting: no new family (merge/quick need live recursion), but the
   exchange sort (exponent 2, steps differ from selection by ~1.5x) is
   archived in more seeds than control's 7 of 8 -- weak prediction.

**Falsification.** If prediction 1 fails, cost-profile novelty is not
enough on its own: slower algorithms never reach a full solve inside the
window. The next lever would then be partial credit for not-yet-correct
programs with a novel profile.

## 99 (amended decision rule). Registered 2026-10-11 while the battery ran, before reading any result

Reviewing the rule above found it unsafe in the costly direction. With
10 seeds the per-arm count has SD ~1.3 at p = 0.8, so a skeleton that
truly costs 20% of successes often shows as -1 and would be removed.
Removing is the expensive mistake, keeping is the cheap one, so the rule
is now asymmetric. It also ignored family loss, newer problems that may
use these skeletons, and joint removal. Replaces the rule above:

1. **Keep** if any served problem drops by >= 2 of 10 (unchanged). Final.
2. **Candidate** if every served problem stays within -1 of 10. Not a
   removal by itself.
3. **Confirmation, 30 seeds** (45000-45029, 20 new seeds per candidate
   arm and base). Removable only if, on every served problem, the arm is
   >= base - 3 of 30 and, where base is 30/30, the arm is >= 27/30.
4. **Family (selectionsort only).** Each verified sorting winner of the
   30 seeds is classified by reading the program, criteria fixed now:
   *selection* = an inner loop that tracks a min/max index or value,
   then one swap per outer iteration. Removable only if nosel shows
   selection in >= 1/3 as many seeds as base does (and at least once if
   base shows it at all).
5. **Usage map.** Before removing, grep the winners of the latest modest
   battery (`data/modest_battery_skeleton_pruned_20261004/`) and of base
   here for each candidate's shape. Any other problem whose winner uses
   it joins step 3 as a served problem.
6. **Joint removal.** The skeletons passing 1-5 are removed together in
   one commit, then a full 49-problem modest battery, 10 seeds, removed
   set vs base. Any drop >= 3 reverts the culprit skeleton; a drop of
   exactly 2 gets a 30-seed retest under step 3's threshold, and a skeleton
   is restored if the retest fails. Time is not a criterion.

## 100. Generic scalar-loop piece (`--scalar-loop`) -- design and predictions registered before implementing

Section 99 found that the current pieces never reach arithmetic loops over
a scalar counter, so five skeletons (average, repeatedmultiply,
recurrence, nesteddivisor, nesteddivisornative) are still indispensable.
Note: the combinator is gated on `numVars >= 8` (`genStmt`), and the scalar
problems run with 4-6 vars, so no combinator piece could ever reach them.
The new piece therefore joins the **skeleton draw** (same
`loopAccumulatorBias` trigger, weight 3, only when `--scalar-loop` is on)
and asks for only as many variables as the variant needs.

**The piece.** Inputs X = arr[0], Y = arr[1], N = v0 (length). State a
(result), b, counter i, temp t. Each part is drawn independently:
- init: a in {0, 1, X}; b in {0, 1, Y} (Pair only).
- loop: Counted (`i = s; while (i C B) {...; i = i + 1}`, s in {0, 1, 2},
  C in {<, <=}, B in {X, Y, N}, guard `i * i <= B` with prob. 1/4), or
  UntilZero (`while (b != 0)`, Pair only).
- body:
  - Fold: `a = a OP T`, OP in {+, -, *}, T in {i, X, Y, arr[i]}.
  - Pair: `t = a OP b; a = b; b = t`, OP in {+, -, %}.
  - Divisor test: `if (X % i == 0) U`, U in {a = 0, a = 1, a = a + 1,
    a = a + i}, with an optional pre-guard `if (X < s) a = c`.
- post (prob. 1/4): `a = a / D`, D in {N, X, Y}.
- write `arr[0] = a`.

It needs 2 vars (Fold, Test), 3 (Pair UntilZero) or 4 (Pair Counted), so
Pair-Counted (Fibonacci) needs `numVars >= 5`. fibonacci runs at
`--num-vars 4`, which is a known limitation. The targets are single draws:
factorial (Fold *, i), power (Fold *, X, bound Y), average (Fold +,
arr[i], post / N), gcd (Pair %, UntilZero), is_prime (Test, a = 0, square
guard, pre-guard). The same space also holds divisor counts and sums,
triangular numbers and multiplication by addition, so it is not a
union of the five skeletons. The per-target draw probability is about
1e-3 to 1e-4, against 1/7 for a skeleton.

**A/B.** Script: `scripts/run_scalar_loop_ab.sh`. Same budget and max-n as
section 99, fresh seeds 46000-46009. Arms: base; SL (+ `--scalar-loop`); SLX
(SL with the five scalar skeletons disabled). Problems: average,
factorial, power, gcd, fibonacci, is_prime, plus the controls sorting,
three_sum, graph_reachability and count_distinct, whose skeletons the new
option dilutes.

**Predictions** (of 10):
1. SLX >= 5 on average, factorial and power; >= 5 on gcd; >= 3 on is_prime.
2. SLX fibonacci = 0 (num-vars 4: Pair-Counted does not fit).
3. SL >= base - 1 on all ten problems (one extra option of the ~8 dilutes
   the others only slightly).

**Decision rule.** `--scalar-loop` becomes default only if prediction 3
holds and a full modest battery shows no regression (section 99 amended,
step 6). A scalar skeleton becomes a *candidate* for removal only if SLX
stays within -1 of base on every problem it serves, and is then removed
only through section 99's amended steps 3-6 (30 seeds, joint removal,
full battery).
