## 116. Diagnosis of equilibrium_point (user request; it stops being an independent held-out problem)

Facts:
- Solvable in Mini-C: a hand-written two-pass reference passes every
  generated, adversarial and exhaustive instance
  (`equilibrium_point_has_a_two_pass_reference_solution`).
- Every run (0/80 over sections 114-115) stalls at level 2, best 58-72 of
  74. Labels at n = 2 are -1:33, 0:17, 1:12; at n = 4 -1:81 of 134. So a
  constant -1 already scores about half, and the search sits just above.
- The reference needs four ingredients:
  1. a first pass leaving the total in a variable;
  2. a second pass with a running prefix sum;
  3. a test that mixes both: `prefix == total - prefix - a[i]`;
  4. "first index where the test holds, else -1": `r = -1` before the
     loop, `if (r < 0 && test) r = i` inside it.
- What the generator emits: (2) exists (Sum, ResetSum, scalar loop);
  (1) exists only as a block's private accumulator, and no block reads
  another block's variable except by chance; (3) no piece builds a
  comparison of an element against an expression of two accumulators;
  (4) **no piece emits it at all**: Exists sets a flag, arg-best returns
  the index of the best value, Place keeps an index for a swap; nothing
  returns the first index satisfying a predicate, and -1 appears only as
  the section 113 sentinel (after an arg-best FrequencyTable pass).

Reading: ingredient 4 is a missing relation, not a gradient problem.
`search_rotated` (first index equal to the key, else -1, 2/70) needs
exactly the same relation and nothing else, so the two external failures
share one gap. equilibrium_point additionally needs cross-pass data flow
(1 + 3), a second, harder gap: one block consuming another block's
result, which no piece expresses.

Proposed next step (not run): a "first index" relation (FirstIndex: r =
-1; first i with `a CMP rhs` sets r = i) as one more single-loop relation.
search_rotated would test it directly; equilibrium_point would still need
the cross-pass ingredient, and is expected to stay at 0 with it.

## 117. Closing section 116's two gaps (`--first-index`, `--prefix-split`) -- registered before implementing

Both are opt-in GenConfig flags, byte-identical off.

**FirstIndex (gap 4).** One more single-loop combinator relation, drawn
one time in six on a single loop with the flag on: `r = -1` before the
loop; inside, `if (r < 0) { if (a CMP rhs) r = i; }`; r is the result.
`a`, `rhs` and CMP come from the block's existing operand and comparator
draws (element vs key or constant), and i is the loop index, so on the
key-prefixed layout r is an array index.

**PrefixSplit (gaps 1 + 3).** A seventh stateful piece, drawn one time in
seven with the flag on (two loop slots): a first pass leaves T = sum of
the elements; a second pass keeps P = sum before i and S = T - P - elem(i)
= sum after i, and feeds `P CMP S` (CMP drawn) to one aggregator of
{first index (-1 default), count, exists}. This is the cross-pass
dependency in its most common form (prefix vs suffix of one array), not
general block-to-block data flow.

## 119. Generic divide-and-conquer shell (`--dc-shell`) -- design registered before implementing

**Problem** (sections 57, 92-93, 118). Recursion exists only inside the
hand-written merge sort skeleton. `--recursion-call-bias` draws a bare
`call(e, e)` with random arguments, which never forms the guard + midpoint +
two-half-calls shape, so no search has ever found a recursive program from
generic pieces. Every failed lever in section 118 left reachability as the
limit; this adds one reachable shape.

**Piece** (opt-in `--dc-shell BIAS`, needs `--recursion-call-bias > 0` and
`--num-vars >= 5`; v1/v2 are lo/hi as in the interpreter's convention,
seeded 0/n at the top level). A top-level statement draw returns
```
if ((v2 - v1) > 1) {
  v3 = v1 + (v2 - v1) / 2;
  call(v1, v3);
  call(v3, v2);
  <combine: 1-2 statements from the ordinary grammar, generated inside an if>
}
```
The combine step is NOT designed: it is whatever the generic grammar draws
(array assignments, conditionals, swaps, loops), so the piece names a shape
(recursion over halves) and leaves the algorithm to the search. It is not
a skeleton: nothing in it is specific to a problem.

**Why this can produce a new algorithm.** For an associative reduction the
correct combine is one statement, `arr[v1] = f(arr[v1], arr[v3])`: a tree
reduction in O(n) steps and O(log n) depth, structurally different from the
accumulator loop every current solution uses. It is reachable level by level
(N=1: guard false, arr unchanged; N=2: one combine).

**A/B.** Arms: control (`--recursion-call-bias 0.1`) vs `+ --dc-shell 0.15`,
matched seeds 3001-3010, the modest-battery profile (beam 500, candidates
1500, step limit 5000, max-n 10, num-vars 7, wall 240 s, `--benchmark`),
problems sum, min, max, single_number, contains, count. Judge by program text
and the independent verification, not by the label.

**Predictions.**
1. The shell yields at least one verified recursive reduction (a `call` that
   runs, no loop over the whole array) for sum in at least 3 of 10 seeds;
   control: 0 (no recursive program has ever been found without the merge
   skeleton).
2. Min and max (combine needs a conditional) are rarer: at most half of sum's
   rate. single_number (xor) is like sum.
3. No loss on any problem versus control (section 99 tolerance, -3 of 10).

**Falsification.** Prediction 1 failing means a random combine is not
reachable even for the one-statement reduction; the next lever would be a
combine drawn from the combinator's two-operand relations.

**Decision rule, fixed now.** Merge policy: it stays opt-in unless it adds
a family on a problem where the control had none and costs nothing elsewhere.
A new family, even a slower or odd one, counts: that is the project's goal.

## 120. Open-specification problems: the checker is a property, not one reference answer -- design registered before running

1. any_peak is solved in >= 7/10 seeds; peak_element reproduces ~3/10
   (section 114). Accepting any peak removes the exact "first peak" ordering

2. Verified any_peak solutions fall into >= 2 behavior classes over the 10

## 121. One-call interval shell (`--dc-shell-search`) on any_peak -- design registered before running

Combination of ideas 1 and 2, requested after section 120. Section 120 left
the binary-search peak unreached; section 119 showed the two-call shell never
becomes a reduction. A peak search needs ONE recursive call on a chosen half,
so a new opt-in shell `--dc-shell-search BIAS` (needs `--recursion-call-bias`
> 0, numVars >= 5, `make test` 235/235) emits:

    if ((v2 - v1) > 1) { v3 = v1 + (v2 - v1)/2;
        if (arr[v3] OP arr[v3 +- 1]) call(v3 + {0,1}, v2) else call(v1, v3 + {0,1}) }
    else arr[0] = (v1 | v2 - 1)

OP in {<, <=, >, >=}, neighbour side, half offsets and the base value are
drawn at random; the shell fixes only the interval-halving shape and the
else-branch write. It does NOT fix which combination is correct. Honest
caveat: this is a strongly shaped piece, close to a skeleton for interval
searches; it is judged as the generic piece it is meant to be by whether it
helps problems other than the one it was designed on (see decision rule).

**Protocol** (`scripts/run_dc_search_ab.sh`): any_peak, seeds 59000-59009, the
section 120 settings plus `--recursion-call-bias 0.1 --profile-novelty 0.5
--profile-ban`; arms base (no shell), search (`--dc-shell-search 0.15`),
search_noloop (`--dc-shell-search 0.15 --no-scalar-loop --combinator-bias 0`).
A hit = engine SUCCESS with adversarial all passed, contains `call(`, no
`while`, and step exponent < 0.5 on an ascending array (worst case for the
early-exit scans), re-executed outside the engine.

**Predictions.**
1. Hits in the search arm: >= 1 of 10 seeds; base: 0 (no `call(` peak search
   has ever been found).
2. search_noloop: >= 1 hit as well, and more hits than search (the loop no
   longer wins the size race, as in section 119).
3. No loss in solved count for search versus base (tolerance -1 of 10).

**Decision rule.** If predictions 1 holds, the shell stays opt-in and is
reported as the first logarithmic result, but promotion needs it to help a
second problem (a different search shape, tested next); a hit only on any_peak
is reported as a skeleton in disguise. If prediction 1 fails, honest negative.
